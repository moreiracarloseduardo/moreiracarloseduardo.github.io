Technical Analysis: WaterPuzzle - Shader-Driven Physics in Godot

WaterPuzzle is a mobile puzzle game developed in Godot 4, where players must organize colored liquids by pouring them between cans until each container holds only one pure color. The project showcases advanced shader programming, spring physics simulation, and procedural puzzle generation without relying on heavy 3D physics engines.

This project demonstrates mastery in GLSL shader programming, physics simulation, procedural generation, and performance optimization for mobile platforms. The entire liquid behavior—from surface waves to inertia—is achieved through custom shaders and spring physics, resulting in realistic visuals at minimal performance cost.

The Challenge: Realistic Liquid Without 3D Physics

Simulating realistic liquid behavior is computationally expensive. Traditional approaches using particle systems or fluid dynamics are prohibitive for mobile devices. The challenge was to create convincing liquid physics—including surface tension, wave propagation, inertia, and multi-colored layering—using only 2D shaders and mathematical models.

Additionally, the game needed to support dynamic difficulty levels with varying can capacities (3-8 units), multiple liquid colors with distinct visual properties, smooth pour animations with realistic timing, and maintain 60 FPS on mid-range mobile devices.

Solution 1: Multi-Layer Liquid Shader with Surface Physics

The core innovation is a custom GLSL shader (liquid_lab.gdshader) that renders up to 8 distinct liquid layers with individual colors, realistic surface behavior, and advanced visual effects. The shader operates entirely in UV space, transforming coordinates based on the can's tilt angle to simulate gravity.

Key Shader Features:

  • Gravity-Based UV Transformation: Uses a rotation matrix to align the liquid surface with the gravitational vector, making the liquid always "level" regardless of can orientation.
  • Multi-Layer System: Supports up to 8 color layers with smooth blending between boundaries. Each layer has configurable blend amounts for vertical and horizontal transitions.
  • Meniscus Effect: Simulates surface curvature near the can walls using pow(abs(x_offset), 3.0) for physically accurate concave/convex shapes.
  • Wave Propagation: Sine-based wave generation with configurable frequency and amplitude, synchronized with game time.
  • Sloshing Simulation: Horizontal oscillation using phase-shifted sine waves to simulate liquid momentum during pour animations.
  • Rim Lighting: Edge detection using mask alpha gradients to create realistic highlights at liquid boundaries.
// Core gravity transformation in liquid_lab.gdshader
mat2 rotation_matrix(float angle) {
    float cos_a = cos(angle);
    float sin_a = sin(angle);
    return mat2(vec2(cos_a, sin_a), vec2(-sin_a, cos_a));
}

void fragment() {
    // Transform UV coordinates based on can tilt
    vec2 center_uv = UV - vec2(0.5);
    vec2 gravity_uv = rotation_matrix(tilt_angle) * center_uv + vec2(0.5);
    
    // Calculate surface position with multiple effects
    float surface = base_surface + inertia_shift + slope_offset + meniscus + wave + slosh;
    
    // Determine if pixel is above or below liquid surface
    float liquid_factor = smoothstep(
        surface - surface_smoothing, 
        surface + surface_smoothing, 
        gravity_uv.y
    );
    
    // Sample correct layer color based on depth
    vec4 final_color = sample_layer_color(depth_ratio_flat, depth_ratio_slope, gravity_uv);
    
    // Apply rim lighting at edges
    final_color.rgb = mix(
        final_color.rgb * (1.0 + rim_light_boost), 
        final_color.rgb, 
        edge_lerp
    );
    
    COLOR = final_color;
}

Solution 2: Spring Physics for Liquid Inertia

To complement the shader, I implemented a spring-damper system in GDScript that simulates liquid inertia and surface oscillation. This creates natural-looking "lag" when the can rotates, making the liquid feel like it has mass and momentum.

Physics Components:

  • Surface Angle Physics: Spring system with configurable stiffness (18.0) and damping (7.5) that makes the liquid surface gradually align with gravity.
  • Surface Offset: Lateral displacement based on angular velocity, simulating liquid "sloshing" to one side during rotation.
  • Adaptive Damping: Higher damping when vertical (0.88) to reduce oscillation at rest, lower when tilted (0.94) for more dynamic movement.
  • Per-Liquid Profiles: Different wave, meniscus, and highlight multipliers for each color type (e.g., water is wavier, syrup has stronger meniscus).
# Spring physics system in can.gd
func _advance_surface_physics(delta: float, current_rotation: float) -> void:
    # Calculate target angle (gravity direction)
    var target_angle = -current_rotation if surface_angle_mode == SurfaceAngleMode.NATURAL else 0.0
    
    # Spring-damper model for surface angle
    var angle_error = target_angle - _surface_angle
    var angle_force = angle_error * surface_angle_stiffness
    _surface_angle_velocity += angle_force * delta
    _surface_angle_velocity -= _surface_angle_velocity * surface_angle_damping * delta
    _surface_angle += _surface_angle_velocity * delta
    
    # Calculate lateral offset from rotation and velocity
    var angular_velocity = (current_rotation - _previous_rotation) / delta
    var target_offset = current_rotation * surface_offset_from_angle
    target_offset += angular_velocity * surface_offset_from_speed
    
    # Spring-damper for offset
    var offset_error = target_offset - _surface_offset
    var offset_force = offset_error * surface_offset_stiffness
    _surface_offset_velocity += offset_force * delta
    _surface_offset_velocity -= _surface_offset_velocity * surface_offset_damping * delta
    _surface_offset += _surface_offset_velocity * delta
    
    # Update shader uniforms
    var mat = liquid_shader_rect.material as ShaderMaterial
    mat.set_shader_parameter("surface_angle", _surface_angle)
    mat.set_shader_parameter("surface_offset", _surface_offset)
    
    _previous_rotation = current_rotation

Solution 3: Optimized Pour Animation System

The pour animation is the most complex interaction, involving three phases: approach (rotating the source can), transfer (liquid flowing out and in), and return (can rotation back to rest). The challenge was making this feel natural while maintaining responsiveness.

Performance Optimization:

I implemented an overlapping animation system that starts the liquid transfer 0.4 seconds before the rotation completes. This creates a more fluid visual experience and reduces total animation time from ~2.8s to ~2.0s—a 28% improvement in responsiveness.

# Optimized pour timing in first_screen.gd
func begin_move(source_idx: int, dest_idx: int):
    # Phase 1: Start rotation
    var approach_tween = source_tube_node.play_pour_approach(dest_tube_node)
    var approach_duration = source_tube_node.POUR_ROTATE_TIME  # 1.0s
    
    # ⚡ OPTIMIZATION: Start pour BEFORE rotation completes
    const OVERLAP_TIME = 0.4  # Start liquid transfer 0.4s early
    var wait_before_pour = max(approach_duration - OVERLAP_TIME, 0.1)
    
    await get_tree().create_timer(wait_before_pour).timeout
    
    # Phase 2: Liquid transfer (now overlapping with rotation)
    var pour_duration = clamp(0.25 + 0.22 * float(pour_count), 0.45, 1.2)
    start_pour_stream_effect(dest_idx, source_idx, pour_duration)
    
    source_tube_node.animate_liquid_pour_out(original_colors, final_colors, color_map, pour_duration)
    dest_tube_node.animate_liquid_pour_in(original_colors, final_colors, color_map, pour_duration)
    
    await get_tree().create_timer(pour_duration).timeout
    stop_pour_stream_effect(dest_idx, source_idx)
    
    # Phase 3: Return immediately (no pause)
    var return_tween = source_tube_node.play_pour_return()
    if return_tween:
        await return_tween.finished
    
    commit_move()  # Apply logical state change

Solution 4: Procedural Puzzle Generation & Validation

Puzzles are generated using a reverse-solve algorithm: start from the solved state (each color in its own can) and apply random valid moves to shuffle. This guarantees every puzzle is solvable. A separate validation system verifies solution integrity and detects impossible states.

Generation Features:

  • Difficulty Levels: Support for 3-8 unit capacities with increasing complexity.
  • State Validation: Real-time checks ensure conservation of liquid units and color counts.
  • Undo/Redo System: Full state history with deep copy to prevent reference bugs.
  • Solution Tracking: Debug system displays optimal solution path for testing.
# Validation system from first_screen.gd
func _quick_validate_state() -> bool:
    var totals := {}
    var total_units := 0
    
    # Count all liquid units by color
    for tube in current_state:
        if tube.size() > tube_capacity:
            push_error("❌ Tube exceeds capacity!")
            return false
        for color_id in tube:
            totals[color_id] = totals.get(color_id, 0) + 1
            total_units += 1
    
    # Verify conservation laws
    var unique_colors = totals.keys().size()
    var expected_units = unique_colors * tube_capacity
    
    if total_units != expected_units:
        push_error("❌ Unit conservation violated! Has: %d, Expected: %d" % [total_units, expected_units])
        return false
    
    # Verify equal distribution
    for color_id in totals.keys():
        if totals[color_id] != tube_capacity:
            push_error("❌ Color %d has %d units, expected %d" % [color_id, totals[color_id], tube_capacity])
            return false
    
    return true

Software Architecture & Design Patterns

The project employs several software engineering best practices:

  • State Machine Pattern: Pour animations managed as explicit states (idle → animating → committing) to prevent race conditions.
  • Singleton Autoloads: PuzzleLogic and SolutionValidator provide centralized game rules and validation.
  • Observer Pattern: Group notifications (add_to_group("first_screen")) for decoupled difficulty changes.
  • Component-Based Design: Can class is fully self-contained with its own shader, physics, and animation logic.
  • Separation of Concerns: Visual staging (shader animations) separated from logical commits (state changes).

var is_animating_move: bool = false
var pending_move: Dictionary = {}

func begin_move(source_idx: int, dest_idx: int):
    if is_animating_move:
        return  # Prevent overlapping moves
    is_animating_move = true
    
    # Store move metadata for later commit
    pending_move = {
        "source_idx": source_idx,
        "dest_idx": dest_idx,
        "pour_count": pour_count,
        # ... other data
    }
    
    # Execute visual animation...
    await animation_complete
    
    # Commit logical state AFTER visuals
    commit_move()

func commit_move():
    if pending_move.is_empty():
        return
    
    # Validate before applying
    if not _quick_validate_state():
        push_error("Invalid state detected!")
        return
    
    # Apply logical changes...
    is_animating_move = false
    pending_move.clear()
